# 토큰 사용량 측정

NyangTracker가 LLM 4종(Codex · Claude Code · Cursor · Gemini CLI)의 토큰 사용량을 **무엇을 읽어서, 어떻게 계산하고, 어떻게 동기화하며, 문제가 생기면 어떻게 조치하는지**를 한 문서로 정리합니다.

구현 현황 기준(2026-08): Codex([codex-usage.md](./codex-usage.md))와 Claude Code([claude-code-adapter.md](./claude-code-adapter.md))는 구현 완료, Gemini/Cursor는 설계 확정 상태이며 각각 마일스톤 M5/M6에서 구현합니다([dev/implementation-plan.md](./dev/implementation-plan.md)).

## 1. 측정 원칙

측정 설계 전체를 지배하는 신뢰 모델은 세 축입니다([architecture.md](./architecture.md)).

| 축 | 정의 | 예 |
|---|---|---|
| **로컬 관측** | provider가 디스크에 남긴 durable 로그에서 직접 읽은 값 | Codex rollout JSONL의 `token_count` |
| **서버 관측** | provider 서버가 준 한도·사용량·과금 데이터 | Codex `rate_limits`(percent), Cursor `chargedCents` |
| **추정** | 가격표·토크나이저 등으로 계산한 파생값 | 모델 단가 × 토큰 (M7) |

세 값은 **저장과 표시 모두에서 분리**합니다. 오픈소스 트래커들의 실패 사례에서 도출한 규칙 R1~R8([dev/token-measurement-survey.md](./dev/token-measurement-survey.md))이 그 근거이며, 이 문서에서 자주 쓰는 것만 요약하면:

- **R1** 중복 제거는 last-wins — 스트리밍 중간 기록 뒤에 오는 최종값을 채택 (ccusage [#888](https://github.com/ccusage/ccusage/issues/888) 실측: first-wins는 하루 약 51.7만 output 토큰 과소)
- **R3** 누적 카운터는 반드시 diff, 감소는 리셋 후보 — 리셋 시 전체 누적값을 사용량으로 기록하지 않음
- **R4** 캐시 읽기 토큰은 input에 합산하지 않음 (이중 계상 금지)
- **R5** 백분율 한도는 토큰으로 변환하지 않음 — 한도 원장과 토큰 원장은 끝까지 별도 테이블
- **R7** 로그에 없는 값은 0이 아니라 "미확인"
- **제품 규칙**: *정직한 불완전 측정이 정밀해 보이는 조작 측정보다 낫다*

## 2. 공통 측정 파이프라인

```text
provider 원본 (파일 / API / 텔레메트리)
        │  어댑터: detect → 과거 스캔 → 증분 관측 (service/providers/<id>/)
        ▼
정규화 이벤트 { delta, eventKey, measurementSource, measurementQuality, fieldQuality }
        │  엔진: service/engine.mjs
        ▼
SQLite usage.sqlite3 (사용자 데이터 디렉터리, NYANG_USER_DATA로 재지정 가능)
  ├ usage_events            ← 토큰 원장 (로컬/서버 관측)
  ├ server_usage_snapshots  ← 한도 원장 (percent — 토큰과 절대 혼합 금지)
  ├ sessions / reconciliation_events / provider_scan_state
        ▼
집계 → GET /api/v1/snapshot + SSE(/api/v1/events) → 대시보드
```

토큰은 공용 7필드로 정규화합니다: `inputTokens`, `cachedInputTokens`, `cacheWriteInputTokens`, `outputTokens`, `reasoningTokens`, `toolTokens`, `totalTokens`. provider가 제공하지 않는 필드는 0으로 저장하되 `fieldQuality`에서 제외해 UI가 "0 토큰"과 "측정 불가"를 구분합니다.

저장 전략은 provider가 고릅니다. Codex는 로그가 append-only라 `insertUsageEvent()`(있으면 무시)를 쓰고, Claude는 같은 요청이 여러 줄로 나뉘어 최종값이 뒤에 오므로 `upsertUsageEvent()`(`(provider, event_key)` UNIQUE + last-wins)를 씁니다. 전역 동작을 바꾸는 것이 아니라 **어댑터가 자기 회계·저장 전략을 선언**하는 구조입니다.

품질 등급은 4단계이며 이벤트 전체 등급은 필드 중 최저치를 따릅니다: `server_verified`(서버 검증됨) > `local_exact`(로컬 관측) > `partial`(추정) > `unverified`(미확인).

## 3. LLM 4종별 측정 방식

### 3.1 Codex — 구현 완료 (참조 구현)

| 항목 | 내용 |
|---|---|
| 원본 파일 | `~/.codex/sessions/**/*.jsonl`, `~/.codex/archived_sessions/**/*.jsonl` |
| 토큰 레코드 | `event_msg.payload.type === "token_count"` |
| 메타데이터 | `session_meta`(세션), `turn_context`(모델·cwd) |
| 파서 | `service/providers/codex/parser.mjs` |
| 품질 | `local_exact` |

**계산 알고리즘** — Codex 로그에는 누적 스냅샷(`total_token_usage`)과 턴 증분(`last_token_usage`)이 함께 옵니다. 파서는 둘을 교차 검증합니다:

1. 누적 총합이 변하지 않았으면 오래된 `last_token_usage`의 재전송(rate-limit-only replay)으로 보고 무시
2. 누적이 단조 증가하면 `last_token_usage`를 채택, 없으면 누적 diff로 대체 (`incrementSource`에 근거 기록)
3. 작은 역행은 순서 뒤바뀜/낡은 스냅샷으로 분류
4. 큰 리셋은 `last_token_usage`만 계상 — 리셋 후 전체 누적값을 사용량으로 절대 잡지 않음 (R3, `cumulativeReset` 플래그)
5. `eventKey = codex|세션|타임스탬프|모델|토큰 6종`으로 활성/아카이브 사본 이중 계상 방지 (fork는 부모 세션 id 유지)

**토큰 회계** — 범주가 서로 겹칩니다. 아래 관계는 ccusage와의 교차 검증(§5.4)으로 확인했습니다.

```text
input  = 비캐시 입력 + 캐시 읽기      ← cached 는 input 안에 포함
total  = input + output               ← 캐시 쓰기는 total 밖
output ⊇ reasoning
```

그래서 화면의 누적 막대는 `total`을 이루는 네 조각(캐시 읽기 · 비캐시 입력 · 출력 · 추론)만 쌓고, 캐시 쓰기는 "합계 외" 항목으로 따로 표시합니다. 다섯 범주를 그대로 더하면 실제의 약 1.9배가 되어 규칙 R4를 어깁니다.

**실제 로그로 확인된 사실** (Codex CLI 0.146.0 rollout 1건, 2026-08). 아래는 합성 픽스처가 아니라 실제 로그와 ccusage 대조로 확정한 내용이며, 회귀 테스트는 `test/codex-real-shape.test.mjs`에 있습니다(프롬프트 본문과 실제 경로는 담지 않고 구조만 옮김).

- `cache_write_input_tokens` 필드는 **실재합니다**. 다만 이 표본에서는 0이고 ccusage도 0으로 보고합니다 — 값이 채워지는 조건은 아직 확인하지 못했습니다.
- 토큰 회계 항등식이 실제 값에서 성립합니다: `19703 + 71 = 19774`, cached 6912 ⊆ input, reasoning 34 ⊆ output.
- `rate_limits.primary`가 **주간 창(10080분)이고 `secondary`가 null**인 경우가 실제로 존재합니다. `primary`/`secondary`는 전송 레인 이름일 뿐이므로 5시간/주간 라벨은 반드시 `window_minutes`에서 파생해야 합니다 — 레인 이름으로 단정하면 이 로그에서 바로 틀립니다.
- 아직 쓰지 않는 신규 필드: `rate_limits.credits{has_credits,unlimited,balance}`, `plan_type`(예: `team`), `individual_limit`, `spend_control_reached`, `rate_limit_reached_type`, `info.model_context_window`, `turn_context.workspace_roots`. 저장하지 않고 있으며, 필요해지면 서버 관측 원장에 추가합니다.
- `cwd`가 Windows 경로(`C:\...`)일 수 있습니다. 로그를 쓴 기계와 읽는 기계의 OS가 다를 수 있어(WSL 등) 프로젝트명 추출은 호스트의 경로 구분자에 의존하지 않습니다.

**서버 한도** — 같은 `token_count` 이벤트의 `rate_limits`는 `(limit_id, window_type, window_minutes)` 키로 `server_usage_snapshots`에 따로 저장합니다. percent → 토큰 변환은 하지 않습니다(R5). 5시간/주간 라벨은 `window_minutes`에서 파생합니다.

### 3.2 Claude Code — 구현 완료

| 항목 | 내용 |
|---|---|
| 원본 파일 | `${CLAUDE_CONFIG_DIR:-~/.claude}/projects/<project>/<대화-id>.jsonl` (+ 서브에이전트 `<session>/subagents/agent-*.jsonl`, 워크플로 `subagents/workflows/<run>/*.jsonl`) |
| 토큰 필드 | `message.usage.{input_tokens, output_tokens, cache_read_input_tokens, cache_creation_input_tokens, output_tokens_details.thinking_tokens}` |
| 계산 방식 | 레코드가 이미 요청 단위 — 누적 diff가 아니라 **값 그대로 저장** (Codex 알고리즘 재사용 금지) |
| 중복 제거 | `event_key = claude|message.id|requestId`, **last-wins UPSERT** (역행 방지 가드 포함) |
| 파서 | `service/providers/claude/{detector,parser,collector,hooks}.mjs` |
| 서버 한도 | JSONL에 없음 → `serverQuota = false` |
| 품질 | 필드별로 다름 — 아래 표 |

**토큰 회계** — Codex와 **다릅니다.** Anthropic API 회계에서 `input_tokens`는 캐시를 제외한 입력이고, 캐시 읽기·쓰기는 그 밖에 따로 있습니다.

```text
프롬프트 = input(비캐시) + cache_read + cache_creation   ← cached 는 input 밖
total    = 위 세 조각 + output                            ← 캐시 쓰기는 total 안
output  ⊇ reasoning(thinking)
```

Codex는 `cached ⊆ input`이고 캐시 쓰기가 `total` 밖입니다. 그래서 어댑터는 `capabilities.tokenAccounting`으로 자기 회계를 선언하고(`cache_in_input` / `cache_disjoint`), 대시보드의 누적 막대는 **provider id로 분기하지 않고 숫자가 어느 항등식을 만족하는지 보고** 분해합니다(`src/shared.js`의 `decomposeTokens`). 캐시 적중률 분모도 회계에 맞춰 계산합니다 — `cached / input`을 그대로 쓰면 Claude에서 수천 %가 나옵니다.

**중복 제거가 이 어댑터의 핵심입니다.** 같은 요청이 content block(thinking / text / tool_use) 단위로 여러 줄에 걸쳐 기록되고, 세션을 resume하면 이전 transcript가 새 파일로 복사됩니다. 실측 코퍼스(214 파일, assistant 레코드 30,753건)에서 전략을 바꿔가며 같은 파서를 돌린 결과:

| 전략 | 요청 수 | 출력 토큰 | 합계 |
|---|---|---|---|
| 중복 제거 없음 | 30,753 | 33,767,537 | 8,487,247,740 |
| 파일 단위 중복 제거 | 14,975 | 14,469,715 | 4,386,086,952 |
| 전역 first-wins | 13,757 | 12,388,371 | 4,006,304,526 |
| **전역 last-wins (채택)** | **13,757** | **13,353,519** | **4,007,269,674** |

- first-wins는 출력 **964,290 토큰(7.22%)을 놓칩니다** — ccusage 이슈 [#888](https://github.com/ccusage/ccusage/issues/888)이 보고한 현상을 우리 로그에서 그대로 재현했습니다. 실측상 파일 안에서는 뒤 레코드가 앞 레코드보다 작아지는 경우가 **0건**이라 last-wins == max-wins입니다.
- 파일 단위 중복 제거는 출력을 **8.37% 부풀립니다**. 그래서 중복 제거 키는 파일이 아니라 요청을 가리켜야 합니다.
- 다만 resume 사본이 사용량 0으로 남는 경우가 있어(실측 1건, 858 토큰) 스토어의 upsert에 **역행 방지 가드**를 둡니다. 뒤에 온 레코드가 더 작으면 덮지 않습니다 — 한 파일 안에서는 역행이 없으므로 이 가드는 last-wins를 바꾸지 않고 resume 사본만 걸러냅니다.

**필드별 품질** — 실측으로 확인한 것만 등급을 올립니다.

| 필드 | 등급 | 근거 |
|---|---|---|
| `cachedInputTokens` | `local_exact` | ccusage와 정확히 일치 |
| `cacheWriteInputTokens` | `local_exact` | 동일. TTL 내역과 어긋나는 레코드만 `partial` |
| `inputTokens` | `local_exact` (2.1.143+) | 아래 참고. 버전이 하한 미만이거나 미확인이면 `unverified` |
| `outputTokens` | `local_exact` (2.1.228+) / `partial` | thinking 내역이 있는 버전만 `local_exact` |
| `reasoningTokens` | `local_exact` (2.1.228+) / 미제공 | 필드가 없는 버전은 0이 아니라 키 자체를 비웁니다(R7) |

**실제 로그로 확인된 사실** (Claude Code 2.1.143~2.1.232, 214 파일 / assistant 레코드 30,753건, 2026-08). 합성 픽스처가 아니라 실제 로그와 ccusage 대조로 확정한 내용이며, 회귀 테스트는 `test/claude-real-shape.test.mjs`에 있습니다(프롬프트 본문과 실제 경로는 담지 않고 구조만 옮김).

- **`output_tokens_details.thinking_tokens`가 실재합니다** — 2.1.228부터 등장하고 그 이전 버전에는 필드 자체가 없습니다(실측 0건). 즉 "Claude 로그에는 thinking 필드가 없다"는 조사 시점의 전제는 최신 버전에서 깨졌습니다. thinking ≤ output이 9,176/9,176건에서 성립하므로 추론은 출력의 부분집합으로 다룹니다. 이 값 덕분에 우리는 ccusage가 보고하지 않는 추론 토큰 **1,680,934개**를 따로 보여줍니다.
- **`input_tokens`의 "75%가 0/1 플레이스홀더"는 이 범위에서 재현되지 않습니다.** 실측 `input ≤ 1`은 8.9%이고, 그중 98.8%는 캐시 읽기/쓰기가 프롬프트를 거의 다 흡수한 정상 케이스입니다. 게다가 한 요청의 여러 레코드에서 `input_tokens`는 전혀 변하지 않습니다(스트리밍 중 커지는 값이 아님). 그래서 2.1.143 이상은 `local_exact`로 올렸고, 그 아래·미확인 버전은 `unverified`로 남깁니다. 조사 문서의 수치는 [당시 측정](https://gille.ai/en/blog/claude-code-jsonl-logs-undercount-tokens/) 기준으로 보존합니다.
- **`usage.iterations[]`가 있고, 상위 `usage`는 그 합이 아니라 마지막 항목과 같습니다**(다중 iteration 9건 전부). 즉 한 message가 여러 번 API를 호출하면 상위 값은 앞선 호출을 빠뜨립니다. 상위 값을 조용히 키우지 않고 해당 필드를 `partial`로 내리고 불일치 횟수를 수집 상태에 남깁니다.
- **`cache_creation_input_tokens`가 0인데 `cache_creation.ephemeral_*` 내역은 0이 아닌 레코드가 있습니다**(13건, 합계 차이 2,561 토큰). 둘 다 provider가 기록한 값이라 더 완전한 쪽을 쓰고 필드를 `partial`로 내립니다. ccusage도 내역 쪽을 쓰기 때문에 이 처리로 두 구현이 정확히 일치합니다.
- **서브에이전트 transcript의 `sessionId`는 부모 세션 id입니다.** 그래서 서브에이전트 사용량이 부모 세션·프로젝트로 자연히 귀속됩니다. 부모 transcript의 `toolUseResult.usage` 롤업(실측 9건)은 **계상하지 않습니다** — 세면 이중 계상입니다.
- `model`이 `<synthetic>`이고 `isApiErrorMessage`가 붙은 로컬 오류 자리표시자가 섞여 옵니다(30건, 토큰 전부 0). API 응답이 아니므로 사용량으로 만들지 않습니다.
- `cwd`는 Windows 경로일 수 있고 모든 assistant 레코드에 있습니다. 프로젝트 디렉터리 이름(`C--Users-...`)은 구분자·유니코드가 `-`로 뭉개져 경로 복원이 불가능하므로 `cwd`가 1순위이고, 없을 때만 디렉터리 이름을 그대로 씁니다.
- 아직 쓰지 않는 필드: `server_tool_use{web_search_requests,web_fetch_requests}`, `service_tier`, `speed`, `inference_geo`, `effort`, `attributionAgent`/`attributionSkill`/`attributionMcpServer`, `slug`, `teamName`. 저장하지 않습니다.

**Hook** — `~/.claude/settings.json`에 `SessionStart / Stop / StopFailure / SessionEnd / SubagentStop` 다섯 개를 옵션으로 설치합니다(설치된 2.1.232 바이너리에 실제로 존재하는 이벤트 이름임을 확인). `UserPromptSubmit`은 토큰 정확성에 필요하지 않고 prompt 본문을 받게 되므로 넣지 않습니다. 사용자 설정을 통째로 덮어쓰지 않고 우리 항목만 끼워 넣으며, 수정 전 원본을 `settings.json.nyangtracker.bak`으로 백업합니다.

**선택 보강 경로(OTLP)** — Claude Code 공식 텔레메트리(`claude_code.token.usage`)를 로컬 수신하면 `type`(input/output/cacheRead/cacheCreation) × `model` × `query_source`(main/subagent/auxiliary)가 정확하게 옵니다. 이 값은 `measurement_source='telemetry'`, 품질 `local_exact`로 **JSONL 레인을 덮어쓰지 않고 병렬 보관**하며(R8), 존재하면 기본 표시로 승격합니다. **아직 구현하지 않았습니다**(`capabilities.telemetry = false`) — 설정 방법과 세부는 [claude-code-adapter.md](./claude-code-adapter.md) §11~13 참고.

### 3.3 Cursor — M6

유일하게 **로컬 파일 원장이 없는** provider입니다. 공식 Admin API만 사용합니다.

| 항목 | 내용 |
|---|---|
| 원본 | `POST /teams/filtered-usage-events`(이벤트 단위), `POST /teams/daily-usage-data`(일 단위 보조) |

요청 기반 플랜(`isTokenBasedCall === false`)은 토큰이 아예 없으므로 토큰 이벤트를 만들지 않고(0으로 채우면 R7 위반), 요청 수/금액을 별도 카운터로 저장해 "요청 기반 플랜 — 토큰 미제공"으로 표시합니다. 개인 계정은 Admin API 대상이 아니므로 `detected: true, ledgerAvailable: false` 상태로 연결 안내만 띄웁니다.

## 3.6 절차별 토큰 배분 — "어떤 절차로 얼마를 썼나"

토큰 총량만 보면 답할 수 없는 질문이 있습니다. 실측 1위 세션은 4.74억 토큰을 썼는데 내역이 이랬습니다.

```text
캐시 읽기  470,700,343   (99.4%)
출력           773,304
비캐시 입력     15,012
```

"많이 썼다"의 실체는 새로 만든 양이 아니라 **같은 컨텍스트를 1,113번 다시 읽은 것**이었습니다. 이걸 보이게 하려고 원장 위에 한 계층을 얹었습니다. 화면 설계는 [dev/menus/session.md](./dev/menus/session.md)에 있습니다.

### 대화 본문 없이 절차를 보는 방법

본문 비저장 규칙([claude-code-adapter.md §17](./claude-code-adapter.md))은 그대로입니다. 그런데도 절차를 볼 수 있는 것은 **구조 메타데이터와 본문이 분리되기** 때문입니다.

| 읽는 것 (구조) | 읽지 않는 것 (본문) |
|---|---|
| 사람 프롬프트의 존재와 시각 | 프롬프트 텍스트 |
| 도구 호출의 **이름**(`Bash`, `apply_patch`) | 도구 **입력**(`input.command`) |
| 도구 호출 횟수, 만진 파일 경로 | 도구 출력, 파일 내용 |
| 컴팩션이 일어난 시각 | 컴팩션 요약문 |

`test/session-flow.test.mjs`가 센티넬 문자열로 이 경계를 검사합니다 — 도구 **이름**은 SQLite에 남고 도구 **입력**은 남지 않는지를 바이트 단위로 확인합니다.

### 턴 = 프롬프트 한 번

```text
사람 프롬프트 1개 ─┐
  요청 1           │
  ...              │ = 턴 1
  요청 88         ─┘
다음 프롬프트 ────> 턴 2
```

턴이 있어야 "프롬프트 한 번에 얼마"가 나옵니다. 실측: 어떤 턴 하나가 세션 전체의 15.8%(73.9M)를 썼고, 그 한 프롬프트에서 요청 88개가 파생됐습니다.

턴 경계의 근거는 provider마다 다릅니다. Codex는 `event_msg/user_message`, Claude는 `type:'user'` 레코드입니다. Cursor는 API가 대화 구조를 주지 않아 **불가**이며, 그때는 0으로 채우지 않고 "미제공"으로 표기합니다([dev/provider-token-api.md §3.5](./dev/provider-token-api.md)).

### 파생 지표 세 개

```text
프롬프트 토큰 = 캐시가 input 밖인 회계(Claude): input + cacheRead + cacheWrite
                캐시가 input 안인 회계(Codex):  input + cacheWrite
재독 배수     = cacheRead / (input + output)
턴 토큰       = 그 턴에 속한 요청들의 (프롬프트 + 출력)
```

**프롬프트 토큰을 provider 회계에 맞춰 더하는 것이 핵심입니다.** Codex는 `cached ⊆ input`이라 그대로 더하면 캐시 읽기를 두 번 셉니다. 회계 표는 `service/providers/accounting.mjs` 한 곳에 두고 어댑터·엔진·스토어가 모두 그것을 봅니다 — 이 값이 두 곳에 흩어져 있던 동안 캐시 적중률이 Claude에서 수천 %로 나왔습니다.

**재독 배수가 높은 것은 나쁜 것이 아닙니다.** 캐시 읽기는 단가가 낮아 "캐시가 잘 듣고 있다"는 뜻일 수도 있습니다. 화면은 배수를 비용 구조의 **성격**으로 제시하고 좋다/나쁘다를 판정하지 않습니다. 금액 환산은 모델별 단가표가 붙는 M7 이후에만 합니다 — 지금 임의 계수를 곱해 "비용"이라 부르지 않습니다.

### 도구 이름으로 작업 단계 분류

정규 단계는 여섯 개(`explore` / `implement` / `verify` / `plan` / `clarify` / `delegate`)이고, 도구 어휘는 provider마다 다릅니다(Claude `Bash`/`Edit`/`Read`, Codex `shell_command`/`apply_patch`/`exec`). 한 턴에 여러 단계가 섞이면 도구 호출 비율로 턴 토큰을 나눠 귀속하며, **인과가 아니라 배분이므로 화면에 "추정 배분"으로 표기**합니다.

실측 예 — 1위 세션의 단계별 배분:

```text
implement   177.9M  37.6%
verify      114.7M  24.2%
explore     109.5M  23.1%
no-tool      63.9M  13.5%
plan          7.8M   1.7%
```

### 저장 구조와 멱등성

집계를 별 테이블에 누적하지 않고, **요청 행에 턴 번호를 달고 집계는 SQL로** 뽑습니다. `usage_events`가 이미 `event_key`로 중복 제거되므로 거기서 파생한 턴 집계는 멱등성을 그대로 물려받고, "턴 토큰 합 == 세션 토큰 합"이 계산으로 보장됩니다. 스키마는 [dev/store-extensions.md §10](./dev/store-extensions.md) 참고.

턴 경계를 못 찾은 구간은 **0번(경계 미확인) 버킷**에 남깁니다. 파일 tail이 중간부터 시작한 경우와, 서브에이전트 transcript의 요청(부모와 세션 id가 같지만 어느 부모 턴에서 시작됐는지 알 수 없음)이 여기 들어갑니다 — 스캔 순서로 아무 턴에 붙이면 거짓이 되기 때문입니다.

## 4. 동기화

### 4.1 실시간 전략 — 의도적 다중화

신뢰도 순서로 여섯 겹입니다. 위가 진실의 원천이고 아래로 갈수록 "빨리 깨우는 신호"입니다.

1. **durable 로그 증분 스캔** — 유일한 진실의 원천
2. **파일시스템 watch** — 빠른 wake-up (`fs.watch`, 이벤트는 힌트일 뿐 내구성 보장 아님)
3. **lifecycle Hook** — 선택적 가속 (Codex: `~/.codex/hooks.json`의 SessionStart/UserPromptSubmit/Stop/SessionEnd, Claude: Stop/StopFailure/SessionStart/SessionEnd/SubagentStop). Hook이 실패하거나 앱이 꺼져 있어도 AI 작업은 계속되어야 하며, 다음 reconcile이 놓친 tail을 재생
4. **주기적 reconcile** — watcher/hook이 놓친 이벤트 복구 (Codex 기본 5초 간격)
5. **브라우저 focus/visibility reconcile** — 절전 복귀·장시간 유휴 후 탭에 돌아올 때 복구
6. **SSE 스냅샷 브로드캐스트** — 정규화 결과를 모든 클라이언트에 전달. 이벤트가 완전한 스냅샷이므로 재연결 시 놓친 델타를 재생할 필요 없음

이 구조 덕분에 **트래커를 꺼둔 채 AI 세션을 진행해도** 다시 켜면 로그 재생으로 따라잡습니다.

### 4.2 증분 커서 2종

`provider_scan_state` 테이블에 provider별로 저장합니다.

```js
// 파일 기반 (Codex / Claude / Gemini)
{ provider, sourcePath, byteOffset, previousUsage, updatedAt }
// Gemini .json 스냅샷 대응 추가 필드: contentHash, parserVersion

// API 기반 (Cursor)
{ provider, sourceKey: 'filtered-usage-events', windowEnd, lastEventTimestamp, page, updatedAt }
```

파일 커서 규칙: 정상 시엔 append된 바이트만 읽고, 불완전한 마지막 줄은 다음 append까지 버퍼링하며, 절단/교체가 감지되면 안전 재스캔으로 폴백합니다. API 커서 규칙: 진행 중인 시간 버킷은 확정값이 아니므로 닫힌 버킷만 전진시키고, 같은 버킷 재요청은 eventKey 중복 제거가 흡수합니다.

### 4.3 서버-로컬 대조 (reconciliation)

연속한 서버 한도 snapshot 사이 구간을 같은 시각의 로컬 토큰 활동과 비교해 `reconciliation_events`에 기록합니다.

| 상태 | 의미 | 처리 |
|---|---|---|
| `MATCHED_ACTIVITY` | 서버 사용률 상승 + 로컬 토큰 관측 | 정상 |
| `SERVER_ONLY_CHANGE` | 서버만 상승, 로컬 근거 없음 | **미귀속 서버 활동으로 보존** — 로컬 토큰에 절대 섞지 않음 (다른 기기·웹 사용 등) |
| `LOCAL_ONLY_ACTIVITY` | 로컬만 상승, 서버 percent 불변 | 정상 (반올림·서버 반영 지연) |
| `RESET` | 리셋 시각 변경 또는 percent 하락 | 한도 창 리셋으로 분류 |
| `UNKNOWN` | 의미 있는 움직임 없음 | — |

### 4.4 단일 인스턴스와 전달 경계

Hook 브리지가 사용자별 고정 소켓을 점유하므로 서비스는 한 프로세스만 뜹니다(두 번째 인스턴스는 즉시 실패). 서비스는 `127.0.0.1` 바인딩 + origin 검사 + 프로세스별 랜덤 토큰(`X-Nyang-Access-Token`)이며, 클라이언트에는 파일시스템 접근이 없습니다. 프롬프트/응답 텍스트와 자격증명은 SQLite·스냅샷·SSE 어디에도 저장하지 않습니다.

## 5. 문제 발생 시 조치

### 5.1 진단 순서

1. **동기화 화면(예정: M4) 또는 `GET /api/v1/diagnostics`** — SQLite 경로, 세션/이벤트/snapshot/스캔 파일 카운터 확인
2. **어댑터 상태** — `getStatus()`가 스냅샷에 실리는 `detected / ledgerAvailable / watching / lastScanAt / lastError`(1줄, 스택 없음) 확인
3. **수동 재스캔** — `POST /api/v1/rescan` 또는 대시보드 "지금 동기화". reconcile은 놓친 tail을 재생하도록 설계되어 있어 대부분의 수집 누락은 이것으로 복구
4. 그래도 안 되면 아래 증상별 표

### 5.1.1 로그 구조 조사

파서가 실제 로그와 어긋나는지 의심될 때는 `node scripts/inspect-codex.mjs`를 실행합니다. 로컬 `~/.codex`(또는 `CODEX_HOME`)를 훑어 **필드 존재 여부와 수치 관계만** 세고, 프롬프트 본문·경로·세션 ID는 출력하지 않습니다. 결과를 그대로 공유해도 안전하도록 만든 리포트라, 이슈에 붙이거나 개발자에게 전달하기 좋습니다.

리포트가 답하는 것: 토큰 회계 항등식이 몇 %에서 성립하는지, `cache_write_input_tokens`가 0이 아닌 사례가 있는지, 한도 레인 조합(primary만 / primary+secondary)과 창 길이 분포, usage·info·rate_limits의 필드 출현, 모델·CLI 버전·plan_type 분포.

### 5.2 증상별 원인과 조치

| 증상 | 원인 후보 | 조치 |
|---|---|---|
| 숫자가 갱신 안 됨 | watcher 이벤트 누락 (에디터의 원자적 쓰기, 네트워크 드라이브, OS별 `fs.watch` 한계) | 주기 reconcile이 자동 복구(기본 5초). 즉시 필요하면 재스캔. watcher는 힌트일 뿐이므로 이 자체는 정상 설계 |
| 수집이 5분 이상 중단 | watcher 오류, 서비스 프로세스 문제 | M4의 `collector_stalled` 알림이 감지. 서비스 재시작 → 시작 스캔이 전체 따라잡기 수행 |
| Hook이 동작 안 함 | 앱 종료 상태, hook 설정 훼손, Codex의 hook 신뢰 정책 | Hook은 가속 경로일 뿐이라 **데이터는 유실되지 않음**. 재설치는 UI에서(기존 hook 그룹 보존, `--nyangtracker-hook` 핸들러만 제거). 원본 설정은 `hooks.json.nyangtracker.bak`으로 백업됨 |
| 로그 파일이 잘리거나 교체됨 | 세션 아카이브 이동, 로그 로테이션 | 커서가 절단/교체를 감지하면 안전 재스캔으로 폴백. eventKey가 활성/아카이브 이중 계상 방지 |
| 누적 카운터 역행 (Codex) | 순서 뒤바뀜 or 진짜 리셋 | 파서가 자동 분류: 작은 역행은 무시, 큰 리셋은 `cumulativeReset` 표시 후 증분만 계상. 조치 불필요 — diagnostics의 "누적 리셋" 카운터로 빈도만 관찰 |
| 총합이 다른 도구와 다름 (Claude) | 중복 제거 정책 차이 or 원본 필드 신뢰도 | 먼저 `test/ccusage-claude-crosscheck.test.mjs`를 돌려 어느 필드가 갈리는지 확인. 실측 기준 네 범주와 총합은 ccusage와 **정확히 일치**합니다. 출력만 다르면 상대 도구가 first-wins일 가능성이 높습니다(우리가 더 커야 정상) |
| 출력에 "추정" 배지가 붙음 (Claude) | 2.1.228 미만 로그는 thinking 내역이 없어 output 완전성을 증명할 수 없음 | **정상 동작.** 최신 Claude Code로 만든 로그부터 `로컬 관측`으로 올라갑니다. 배지는 필드별·등급별 건수를 함께 들고 있으니 툴팁에서 비율을 확인 |
| 턴 수가 0이고 단계가 "도구 없음"으로만 나옴 | 파서 버전업 전에 읽은 파일이라 원장에 턴 번호가 비어 있음 | 수집기가 `turn_index IS NULL` 을 감지해 **한 번 자동 재해석**합니다. 즉시 필요하면 재스캔. 재해석은 중복 제거 덕에 합계를 늘리지 않습니다 |
| 턴 토큰 합이 세션 합과 다름 | 턴 집계를 별 테이블에 누적하는 코드가 들어간 경우 | **버그로 취급.** 집계는 `usage_events`의 `turn_index`로 GROUP BY 해야 하며, 그래야 원장의 중복 제거를 물려받습니다 |
| 재스캔 후 Claude 합계가 늘어남 | 중복 제거 키가 파일 단위로 좁아졌을 때 발생 | **버그로 취급.** `event_key = claude\|message.id\|requestId`가 전역 UNIQUE인지 확인. 실측상 파일 단위로 끊으면 출력이 8.4% 부풀어 오릅니다 |
| 같은 요청이 두 번 집계 | 스트리밍 중간+최종 레코드 | last-wins UPSERT가 정상 동작인지 확인(테스트: 중간/최종 순서 주입 → 최종값만 남아야 함). 실패 시 `event_key` UNIQUE 인덱스 확인 |
| 서버 %는 오르는데 로컬 토큰 없음 | 다른 기기/웹에서 사용 | `SERVER_ONLY_CHANGE`로 기록·표시됨. 로컬 값을 보정하지 않는 것이 명세 |
| Cursor 401/403 | API 키 만료·권한 부족·개인 계정 | 설정에서 키 교체(값 회수 API가 없으므로 재발급). 개인 계정은 `ledgerAvailable: false`가 정상 |
| Cursor 429 | 레이트리밋 초과 | 어댑터 가드가 상한 초과 호출을 막는 것이 완료 기준. 발생 시 폴링 간격(기본 1시간) 상향 |
| Gemini 재스캔 후 합계 증가 | `.json` 스냅샷 중복 계상 | `content_hash` 판정과 eventKey 중복 제거 확인 (완료 기준 위반 — 버그로 취급) |
| 로그 포맷 변경 (파서 깨짐) | provider CLI 업데이트 | `parser_version`이 레코드별로 남아 있어 **재해석 대상 선별 가능**. 새 픽스처 추가 → 파서 수정 → 버전 증가 → 해당 버전 레코드만 재파싱. 로컬 JSONL 스키마는 공개 API가 아니므로(안정성 요청: anthropics/claude-code [#49400](https://github.com/anthropics/claude-code/issues/49400)) 파서는 방어적·픽스처 기반으로 유지 |
| 서비스가 두 개 뜸 | 이전 프로세스 잔존 | 소켓 점유로 두 번째는 즉시 실패(정상). 잔존 프로세스 종료 후 재시작 |
| DB 손상/이전 | 강제 종료, 디스크 | `usage.sqlite3`는 사용자 데이터 디렉터리에 단일 파일 — 백업/복원은 파일 복사. M7의 원장 내보내기/가져오기(JSON/CSV)가 이식 경로. 최악의 경우 DB 삭제 후 재스캔하면 **durable 로그가 남아 있는 범위**는 전부 재구축됨 (Cursor는 API 재폴링) |

### 5.3 복구가 안전한 이유

모든 파일 기반 provider의 원장은 **재생 가능**합니다 — 진실의 원천이 우리 DB가 아니라 provider의 durable 로그이기 때문입니다. 첫 스캔은 restart-safe(중단 후 재실행해도 완료된 이벤트를 이중 계상하지 않음)하고, 커서와 eventKey가 "이어서"와 "한 번만"을 보장합니다. 따라서 조치의 기본형은 언제나 **재스캔**이며, 데이터를 손으로 고치는 절차는 없습니다.

### 5.4 ccusage 교차 검증

파서가 조용히 틀어지는 것을 잡기 위해 [ccusage](https://github.com/ccusage/ccusage)를 **검증용으로만** 씁니다. 런타임 의존성이 아니라 devDependency이고, 우리 수집 경로는 ccusage를 전혀 호출하지 않습니다. 같은 픽스처를 두 구현에 먹여 결과를 비교하는 테스트가 `test/ccusage-crosscheck.test.mjs`(Codex)와 `test/ccusage-claude-crosscheck.test.mjs`(Claude)에 있습니다(미설치 환경에서는 자동 skip).

**Codex**

| 항목 | 기대 |
|---|---|
| `totalTokens` · `outputTokens` · `reasoningTokens` · 캐시 읽기 | **정확히 일치** — 두 구현이 같은 누적 diff 규칙에 도달해야 함 |
| `inputTokens` | **의도적 불일치**: `우리 input == ccusage input + ccusage cacheRead`. 우리는 로그 원본대로 캐시를 포함해 저장하고, ccusage는 캐시를 뺀 값을 input으로 보고합니다 |
| 캐시 쓰기 | 실제 로그에 필드가 **존재**하며 표본값은 0, ccusage도 0으로 보고 — 양쪽 일치. 값이 채워지는 조건은 미확인 |

**Claude** — 실제 로컬 코퍼스(214 파일 / 요청 13,757건 / 40억 토큰)를 얼려두고 ccusage 20.0.20과 나란히 돌린 결과입니다.

| 필드 | NyangTracker | ccusage | 차이 |
|---|---|---|---|
| `inputTokens` (비캐시 입력) | 280,935 | 280,935 | 0 |
| `cachedInputTokens` (캐시 읽기) | 3,933,470,648 | 3,933,470,648 | 0 |
| `cacheWriteInputTokens` (캐시 쓰기) | 60,164,572 | 60,164,572 | 0 |
| `outputTokens` (출력) | 13,353,519 | 13,353,519 | 0 |
| `totalTokens` (합계) | 4,007,269,674 | 4,007,269,674 | 0 |
| `reasoningTokens` (추론) | **1,680,934** | 미보고 | — |

- Claude에서는 우리 `inputTokens`가 ccusage와 **그대로 일치합니다**. Codex와 반대인데, Claude 로그의 `input_tokens`가 이미 캐시를 제외한 값이기 때문입니다.
- 유일한 의도적 발산은 **추론 토큰**입니다. ccusage는 Claude의 `output_tokens_details.thinking_tokens`를 보고하지 않고, 우리는 별도 필드로 보여줍니다. 추론은 출력의 부분집합이므로 총합에 다시 더하지 않습니다.
- 캐시 쓰기가 일치하는 것은 우연이 아니라 설계 결정의 결과입니다. `cache_creation_input_tokens`와 TTL 내역이 어긋나는 13건에서 양쪽 모두 더 완전한 내역 값을 씁니다(§3.2).

**일치를 단정하지 않는 이유**: 설계가 의도적으로 갈라질 수 있는 곳이 있습니다. 특히 중복 제거에서 ccusage 구버전은 first-wins였고 우리는 last-wins(R1)라 같은 로그에서도 값이 다를 수 있으며, **그때는 우리 값이 더 커야 정상입니다**(실측 차이: 출력 7.22%). 그래서 이 테스트는 "같아야 한다"가 아니라 합의 항목과 예상 발산 방향을 함께 못박습니다.

이 대조로 실제 결함을 둘 잡았습니다 — Codex 쪽에서는 누적 막대가 캐시 쓰기를 input에서 빼는 바람에 비캐시 입력이 과소 표시되고 있었고, Claude 쪽에서는 `cache_creation_input_tokens`만 믿어 캐시 쓰기 2,561 토큰을 놓치고 있었습니다.
