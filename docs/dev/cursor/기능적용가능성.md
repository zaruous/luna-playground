# Cursor 적용 가능성 표 (M6a)

[LLM별 기능지원표.md](../LLM별%20기능지원표.md)는 Claude/Codex/Gemini/Cursor 4종을
나란히 놓고 **지금 코드가 무엇을 지원하는가**를 봅니다. 그 표의 Cursor 열은 거의
전부 X·△인데, 그 이유가 "신호가 없어서"인지 "신호는 있는데 아직 코드가 없어서"인지가
한 글자로는 안 갈립니다. 이 문서는 그 질문 하나만 봅니다 — **화면/기능 단위로, 이번
M6a 트랙에 Cursor를 적용할 수 있는가.**

판단은 전부 실측에 근거합니다 — [measurements.md](./measurements.md)(무엇이
로컬에 있는지)와 [decisions.md](./decisions.md)(그래서 어떻게 하기로 했는지)를
그대로 인용합니다. 새로 조사한 내용은 없습니다.

## 표기

| 이번 M6a 적용 | 뜻 |
|---|---|
| **가능** | 필요한 신호가 로컬에서 실측 확인됐고, 지금 계획(Phase 1~3)에 이미 들어 있음 |
| **보류** | 신호가 있을 수도 있지만 아직 확인 안 됨(Phase 0b 후속 조사가 끝나야 결정) — 이번 트랙에서 만들지 않음 |
| **배제** | 필요한 신호 자체가 로컬에 없음(항목이 요청 단위 델타를 전제) — Cursor에 억지로 채우지 않음 |

## 대시보드

| 화면/기능 | 필요한 신호 | 로컬 실측 상태 | 이번 M6a 적용 | 비고 |
|---|---|---|---|---|
| provider 카드 총 토큰 표시 | 요청 단위 input/output/cache 델타 | 없음 — 평문 JSON blob 3,629개 + 이진 blob 95,722개 전수 스캔에서 0건 | **배제** | 대신 마지막 관측 `context_total_tokens`/`context_window_tokens`(예: 27,766/200,000)를 표시 |
| 최근 프로젝트 발자국(전체 provider 통합, `last_activity` 정렬) | 대화/컴포저의 최근 활동 시각 | 실측됨 — CLI `meta.json.updatedAtMs`, IDE `composerHeaders.lastUpdatedAt` | **가능** | 이미 있는 시각 정렬 로직에 그대로 얹힘 |
| 캐시 적중률·요청당 평균 카드 | 캐시read + 비캐시input + output | 없음(위와 동일) | **배제** | `accounting: 'context_only'`면 얼리 리턴 |

## 구현 방식 (화면이 아니라 수집 계층)

| 항목 | 필요한 신호 | 로컬 실측 상태 | 이번 M6a 적용 | 비고 |
|---|---|---|---|---|
| SQLite 스냅샷 스캔(byte-offset tail 대신 content-hash) | 없음 — WAL로 재작성되는 SQLite라는 사실 자체가 근거 | 실측됨(`store.db`/`state.vscdb`가 append-only가 아님) | **가능** | Gemini `.json` 전략 재사용(결정 3) |
| 대화 본문 비저장 | 없음 — 오히려 "안 읽는" 것이 요구사항 | 파악됨 — blob의 `role`/`content` 구조, 이진 blob의 필드 경계 | **가능** | `role`/카테고리 키만 취하고 `content`는 파서가 절대 안 엶(결정 2) |

"배제" 10개는 전부 같은 이유(요청 단위 토큰 델타가 로컬에 없음) 아니면 같은 결정
(서버 사용량은 이 트랙에서 안 봄) 하나로 갈립니다 — 항목이 늘어난 것이 아니라
같은 두 제약이 여러 화면에 반복해서 나타난 것입니다. "가능" 10개도 마찬가지로
같은 세 신호(cwd, 컨텍스트 breakdown, 감지 여부)가 여러 화면에 재사용됩니다.
