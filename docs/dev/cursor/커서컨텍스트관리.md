# Cursor 컨텍스트 관리 — 로컬 실측 정리

작성일시: 2026-08-26

이 문서는 [measurements.md](./measurements.md)·[decisions.md](./decisions.md)의
실측 결과 중 "Cursor가 컨텍스트(창)를 어떻게 관리하는가"만 따로 모았습니다. 값은
전부 로컬 blob의 **필드 번호·토큰 수**에서 나온 것이고, 시스템 프롬프트·대화
본문·도구 결과 **텍스트 자체는 이 조사에서도 여전히 읽지 않았습니다** — 아래
"압축 샘플"도 카테고리별 토큰 수 표일 뿐, 실제 요약 문장이나 대화 내용이 아닙니다.

## 데이터 출처

- 필드 경로 `5.1`/`5.2`/`5.3.3[]` — CLI(`~/.cursor/chats/**/store.db`)와
  IDE(`state.vscdb`의 `cursorDiskKV`) 양쪽 이진 blob에서 재귀 protobuf 스캔으로
  확인. 스캐너: `service/providers/gemini/antigravity-protobuf.mjs`의
  `scanProtobuf` 재사용.
- 재현 스크립트: `scripts/probe-cursor.mjs`(전수 스캔·항등식 검증),
  `scripts/probe-cursor-delta.mjs`(대화별 순서 있는 diff·압축 감도).
- 실측 규모: CLI+IDE 이진 blob 95,722개 스캔, breakdown 있는 blob 1,818개(카테고리
  합=총합 불일치 0). 이번 문서의 압축·MCP 관련 수치는 그중 CLI 대화 32개(554개
  구간)로 좁힌 2차 패스(Phase 0b, 2026-08-26) 결과입니다 — IDE 쪽은 blob이
  content-addressed라 대화 귀속 없이는 순서를 못 매겨 이번 패스에서 뺐습니다
  (미확인으로 남김).

## 카테고리 8종 — 정적인 것과 동적인 것

```text
5.1       = 그 시점 컨텍스트 총 토큰 수
5.2       = 컨텍스트 창 크기(관측값: 200000 · 256000 · 272000 · 300000)
5.3.3[]   = 카테고리별 { 키, 표시명, 토큰 수, 문자 수 }
```

관측된 카테고리 8종을 성격으로 나누면:

| 카테고리 | 성격 | Phase 0b 실측 |
|---|---|---|
| `system_prompt` | 정적 | 31개 대화 전부에서 대화 시작 이후 **한 번도 변화 없음** |
| `tools` | 정적 | 동일 |
| `rules` | 정적 | 동일 |
| `skills` | 정적 | 동일 |
| `mcp` | 정적(관측 범위 내) | 동일 — 아래 "MCP와의 관계" 참고 |
| `subagents` | 정적 | 동일 |
| `summarized_conversation` | 동적, 압축 시에만 증가 | 관측 586개 blob 대부분 0, 압축 발생 시점에만 값이 생김 |
| `conversation` | 동적, 매 스냅샷마다 증가(압축 전까지 단조 비감소) | 실질적으로 `5.1` 증가분 전부를 차지 |

**핵심 발견(Phase 0b)**: `system_prompt`~`subagents` 6개 카테고리가 관측된 모든
대화에서 시작 후 고정이었기 때문에, `5.1`(전체) 기준 diff 합계와 `conversation`
카테고리만 기준으로 한 diff 합계가 31개 대화·554개 구간 전부에서 **완전히
동일**(1.00배)했습니다. 즉 이 표본 안에서는 "컨텍스트가 커졌다"는 사실상
"대화가 길어졌다"와 같은 말이었습니다.

## MCP와의 관계

`mcp` 카테고리는 그 대화에 연결된 MCP 서버의 **도구 정의(스펙)** 가 컨텍스트에
얼마나 실리는지를 나타내는 것으로 보입니다 — 관측된 예시 대화에서 `mcp: 1039`로,
대화가 17~206개 스냅샷에 걸쳐 진행되는 동안 **한 번도 바뀌지 않았습니다**. 이는
두 가지를 시사합니다.

1. MCP 도구를 실제로 **호출한 결과**(tool_use 응답 본문)는 `mcp` 칸이 아니라
   `conversation` 칸에 쌓이는 것으로 보입니다 — `mcp` 칸은 "이 대화가 어떤 MCP
   서버·도구를 쓸 수 있는지"라는 스펙 목록 크기에 더 가깝습니다.
2. 이 결론은 **관측 범위 안에서** 그렇다는 것이지 확정은 아닙니다 — 대화 도중에
   새 MCP 서버를 연결하거나 끊는 경우를 이번 표본(32개 대화)에서는 만나지
   못했습니다. 그런 사례가 있다면 `mcp` 칸이 그 시점에 계단식으로 바뀔 것으로
   예상되지만, 이건 미확인입니다.

`tools`(1st-party 도구)·`rules`(룰 파일)·`skills`도 같은 성격 — "이 대화에서 쓸 수
있는 것의 정의 크기"이지 "실제로 얼마나 썼는지"가 아닙니다. 실제 사용량(호출
횟수·호출당 토큰)은 이 breakdown 어디에도 없습니다 — 그건 이미
[measurements.md](./measurements.md#확인되지-않은-것)에 확인 안 됨으로 적어 둔
그대로입니다.

## 토큰 상한(창 크기)과 압축의 관계

`5.2`(창 크기)는 그 대화가 쓰는 모델의 컨텍스트 한도입니다(관측값 200k/256k/
272k/300k — 모델·모드에 따라 다름). `5.1`이 이 한도에 가까워지면 압축이
일어나는 것으로 보입니다. 실측 사례(대화 `eca64170-...`, CLI, 창 200,000):

```text
압축 전 (연속 스냅샷 3개, 5.1 = 186,654 · 창의 93.3%)
  system_prompt 517 · tools 8,079 · rules 3,026 · skills 2,255 · mcp 1,039 ·
  subagents 503 · summarized_conversation 0 · conversation 171,235

압축 후 (연속 스냅샷 2개, 5.1 = 68,810 · 창의 34.4%)
  system_prompt 517 · tools 8,079 · rules 3,026 · skills 2,255 · mcp 1,039 ·
  subagents 503 · summarized_conversation 4,986 · conversation 48,405
```

정적 카테고리(system_prompt~subagents, 합계 15,419)는 전혀 안 바뀌었습니다.
바뀐 건 딱 둘입니다 — `conversation`이 171,235 → 48,405로 줄고,
`summarized_conversation`이 0 → 4,986으로 채워졌습니다. 정리하면:

- 이전 대화 내용 중 **122,830 토큰어치**가 요약 **4,986 토큰**으로 압축됐습니다
  (≈34:1 압축비).
- 가장 최근 **48,405 토큰**은 압축 없이 원문 그대로 남았습니다 — 압축이 대화
  전체가 아니라 "오래된 부분"만 건드린다는 뜻으로 읽힙니다.
- 창의 93.3%가 찬 시점에 트리거됐다는 것도 "상한에 근접하면 압축한다"는 가설과
  맞습니다. (표본 1건이라 정확한 트리거 임계값은 확인 안 됨 — 90%일 수도 95%일
  수도 있습니다.)

### 압축이 서버로 보내는 토큰량에 미치는 영향 (추론, 직접 관측 아님)

**주의**: 아래는 로컬 스냅샷 구조로부터의 추론입니다. 실제 HTTP 요청 바이트를
가로채서 확인한 것이 아닙니다(이 프로젝트는 네트워크 트래픽을 가로채지
않습니다 — R6와 같은 경계).

`5.1`(그 시점 컨텍스트 총합)이 "다음 요청을 보낼 때 모델에 실리는 컨텍스트
크기"의 가장 근접한 로컬 대리 신호입니다. 이 가정 위에서 압축의 실질적 효과는:

- **압축 직전**: 다음 요청 하나를 보내려면 컨텍스트 186,654 토큰어치를 모델에
  실어야 합니다(그중 캐시로 재사용되는 부분이 있다면 실제 과금·연산량은 이보다
  적을 수 있지만, 캐시 히트율은 로컬에서 안 보입니다 — measurements.md의 같은
  한계).
- **압축 직후**: 같은 다음 요청이 68,810 토큰어치로 줄어듭니다 — 창 사용량이
  거의 1/3로 떨어집니다. 이후 대화가 계속되면 `conversation`이 48,405부터 다시
  단조 증가합니다.
- **순 절감량은 122,830 전부가 아니라 117,844**입니다 — 요약 자체가 4,986
  토큰을 영구히 차지하기 때문입니다(요약도 매 요청마다 같이 실립니다).
- 따라서 압축은 "한 번 트리거되면 그 뒤로 한동안 요청당 토큰량이 확 낮아지는"
  톱니 패턴을 만듭니다 — 창이 다시 상한 근처까지 차면 또 압축이 트리거될
  것으로 예상됩니다(반복 관측은 못 했음 — 이 표본엔 대화당 압축이 최대 1번만
  있었습니다).

## Phase 0b 감도 실측 요약

`scripts/probe-cursor-delta.mjs`로 31개 대화·554개 구간을 스캔한 결과(상세는
[decisions.md](./decisions.md#phase-0b-감도-실측-2026-08-26--카테고리-선택은-문제없음-압축-클램프는-필수)):

| 항목 | 값 |
|---|---|
| 카테고리 선택 민감도(전체 vs conversation-only) | 1.00배 (동일) |
| 구간 총합 대비 압축 발생 구간 | 1 / 554 (0.18%) |
| 압축 발생한 대화 | 1 / 31 |
| 압축 1건이 전체 합계에서 차지하는 비율 | 11.67% |

즉 압축은 **드물지만(0.18%) 터지면 큽니다(11.67%)** — 델타를 이어붙여 총합을
낼 때 음수 구간을 그냥 더하면(클램프 안 하면) 이 한 건만으로도 총합이
크게 어긋납니다. 표본이 이 계정 32개 대화뿐이라 이 비율의 일반성은 미확인입니다
— 더 긴 대화가 많은 계정에서는 압축 빈도·영향이 더 클 것으로 예상됩니다.

## 설계 제안: 압축 경계를 세션 분리가 아니라 "구간(seq) 마커"로 다룬다

압축이 만드는 톱니 패턴(위 절)을 어떻게 다룰지 논의하다 나온 대안 두 가지를
비교합니다.

**안 A — 압축마다 새 세션으로 쪼갠다** (`chatId_0`, `chatId_1`, `chatId_2`, ...).
장점은 각 조각이 항상 단조 증가라 클램프가 필요 없어진다는 것. 하지만 이
프로젝트의 세션 정체성은 provider가 주는 실제 대화 ID가 원칙이고, Cursor는 그게
`chatId`(CLI)/`composerId`(IDE) 하나입니다. 압축마다 가상 ID를 새로 만들면:

- "세션 수" 카드가 부풀어 실제 대화 수와 안 맞게 됩니다(사용자 입장에선 Cursor
  화면에서 계속 스크롤되는 **하나의** 대화인데, NyangTracker에서는 여러 개로
  보입니다).
- 프로젝트→세션 매핑, 세션 순위 같은 다른 화면과 정합성을 새로 맞춰야 합니다.

**안 B — 세션은 그대로 두고, 내부적으로 압축 구간 seq(epoch)만 센다.** 이미 이
저장소에 정확히 이 모양의 선례가 있습니다 — `turns` 테이블에 이미 `compacted`
컬럼이 있고([session.md](../menus/session.md) §DB 스키마), Claude·Codex는 압축을
**세션을 쪼개지 않고 턴에 마커만 붙이는** 방식으로 이미 처리 중입니다
(`type:'system'/subtype:'compact_boundary'`, `event_msg.payload.type ===
'context_compacted'`). Cursor도 같은 관례를 따르면:

```text
cursor_compaction_epoch(chat_id, epoch_seq, started_at, boundary_snapshot_total)
```

같은 보조 카운터 하나로 충분합니다 — `chat_id`는 그대로, 압축이 감지될 때마다
`epoch_seq`만 +1. Phase 0b의 클램프 로직은 사실 이 안을 계산상으로는 이미
구현한 것과 같습니다(음수 구간에서 클램프 = 새 epoch 시작, 그 앞뒤를 별도
누산 구간으로 다루는 것과 수학적으로 동일) — 안 B는 그 경계에 **이름**을
붙이고 UI에 "압축 N회"처럼 노출할 수 있게 하는 차이입니다.

**권장**: 안 B. 기존 `turns.compacted` 관례와 일치하고, 세션 개수·순위 등 다른
화면의 정합성을 새로 깨지 않습니다. 다만 이건 M6a가 실제로 이 추정치 기능을
만들기로 결정한 뒤에 붙일 스키마 변경이라, 지금은 설계로만 남겨둡니다 —
[decisions.md 결정 0](./decisions.md#결정-0-이-트랙은-원격-사용량을-다루지-않는다)의
"실측부터, 구현은 그 다음" 순서를 그대로 따릅니다.

## 이 문서가 다루지 않는 것

- 실제 요약 문장·대화 본문 — 절대 안 읽었습니다([measurements.md 경계](./measurements.md#절대-읽지-않은-것-의도적으로-건드리지-않음)와 동일).
- 압축 트리거 임계값의 정확한 수치(90%인지 95%인지) — 표본 1건으로는 확정 불가.
- IDE 쪽(`cursorDiskKV`) 압축 패턴 — 이번 Phase 0b 패스는 CLI만 봤습니다.
- 실제 서버 전송 바이트 — 로컬 스냅샷으로부터의 추론이지 네트워크 실측이
  아닙니다.
