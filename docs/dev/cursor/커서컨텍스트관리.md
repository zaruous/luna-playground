# Cursor AI 컨텍스트 관리와 토큰 압축의 실체 — 로컬 데이터로 직접 확인했다

작성일시: 2026-08-26

## 이 글을 쓴 이유

Cursor를 매일 쓰면서도 정작 "내가 지금까지 토큰을 얼마나 썼는지"를 확인할 방법이
마땅치 않았다. 대시보드에는 팀/엔터프라이즈 전용 사용량 화면이 있지만 개인
계정에는 없고, API 키를 발급해도 두 가지 벽에 부딪힌다.

- Admin API(`/teams/...`)는 실제 사용 이력을 이벤트 단위로 주지만, 조직에서
  Admin 권한을 가진 사람만 키를 발급할 수 있다. 팀 멤버라도 Admin이 아니면
  써볼 수조차 없다.
- 개인 API 키(Cloud Agents API)는 인증은 되지만, 그 키로 조회할 수 있는 사용량은
  "그 API로 새로 실행시킨 작업"에 한정된다. 지금까지 IDE나 CLI로 쌓아온 기존
  대화 이력은 이 API로 조회가 안 된다.

그래서 서버 API를 포기하고 로컬에 뭐가 남아 있는지 직접 열어봤다. 결론부터
말하면 **완전한 토큰 사용량 로그는 없지만, 생각보다 훨씬 많은 정보가 로컬
SQLite 파일 안에 그대로 있었다** — 이 글은 그 구조를 정리한 것이다. 대상은
Cursor IDE(Composer)와 Cursor CLI(`cursor-agent`) 둘 다이고, 실측은 Windows
환경에서 진행했다.

## Cursor는 대화를 어디에 저장하는가

Cursor는 대화 하나(챗/컴포저)를 진행하는 동안 그 내용을 SQLite 기반 로컬
저장소에 청크 단위로 계속 써 내려간다. IDE와 CLI가 쓰는 위치는 다르지만
저장 방식은 같다 — 내용 주소화(해시를 키로 쓰는) key-value 저장소에 대화
조각을 이진(binary) 또는 평문 JSON 형태로 쌓는다.

각 조각(blob)은 첫 바이트로 구분된다.

- `{`나 `[`로 시작하면 **평문 JSON**이다. 시스템 프롬프트, 사용자 질문, 도구
  실행 결과 본문이 그대로 들어 있다.
- 그 외는 **필드 이름이 없는 이진 데이터**다. protobuf 와이어 포맷과 동일한
  구조라 필드 번호와 값만 나열할 수 있고, 이름은 와이어에 없다.

이 글이 다루는 건 두 번째, 이진 blob 쪽이다. 이 안에 대화 본문과는 별개로
**그 순간 컨텍스트 창에 무엇이 얼마나 들어있는지**를 알려주는 구조화된 필드가
있었다.

## 컨텍스트 구성 breakdown — 대화 하나의 "그 순간 청구서"

이진 blob을 일반적인 protobuf 스캐너로 훑으면 이름 있는(!) 하위 구조가
나온다. 와이어 자체엔 필드 이름이 없지만, 이 메시지는 하위 필드 중 하나가
카테고리 이름 문자열 그 자체라서 `system_prompt`, `tools`, `rules`처럼 사람이
읽을 수 있는 라벨이 그대로 노출된다.

구조는 이렇다.

```text
그 시점 컨텍스트 총 토큰 수
컨텍스트 창 크기 (관측값: 200,000 / 256,000 / 272,000 / 300,000)
카테고리별 항목 반복:
  카테고리 키   (예: "system_prompt")
  카테고리 표시명 (예: "System prompt")
  그 카테고리의 토큰 수
  그 카테고리의 문자 수
```

이진 blob 95,722개를 전수 스캔한 결과, 이 breakdown 구조가 있는 blob 1,818개
**전부**에서 카테고리별 토큰 수를 합친 값이 선언된 총합과 정확히 일치했다.
관측된 카테고리는 여덟 가지다 — `system_prompt`, `tools`, `rules`, `skills`,
`mcp`, `subagents`, `summarized_conversation`, `conversation`.

## 여덟 카테고리 중 여섯은 고정값, 둘만 변한다

대화 하나를 처음부터 끝까지 추적하며 각 카테고리가 시간에 따라 어떻게
움직이는지 확인했다(31개 대화, 554개 관측 구간). 결과는 뚜렷하게 갈렸다.

**한 번 정해지면 그 대화 안에서 절대 바뀌지 않는 것**: `system_prompt`,
`tools`, `rules`, `skills`, `mcp`, `subagents`. 이 여섯 카테고리는 관측된 모든
대화에서 시작 시점 값이 끝까지 유지됐다 — 대화가 5턴이든 200턴이든 마찬가지였다.

**대화가 진행될수록 계속 커지는 것**: `conversation`. 이 칸만 스냅샷마다 늘어난다.

**평소엔 0이다가 특정 시점에만 값이 생기는 것**: `summarized_conversation`.
바로 다음 절에서 다룰 압축이 일어날 때만 채워진다.

실제 도구 호출 횟수나 호출 하나하나의 토큰 비용은 이 구조 어디에도 없다 —
있는 건 여덟 카테고리의 토큰 수뿐이다. 이 breakdown은 **컨텍스트 창의 현재
구성**을 보여주는 스냅샷이고, **요청 하나하나가 얼마나 썼는지**를 보여주는
필드는 포함하지 않는다.

## MCP 도구는 컨텍스트를 얼마나 차지할까

`mcp` 카테고리를 따로 볼 이유가 있다 — MCP(Model Context Protocol) 서버를
연결해 쓰는 사용자가 많고, "MCP 도구를 많이 쓰면 토큰을 얼마나 더 쓰게
되는가"는 실용적으로 궁금한 질문이기 때문이다.

관측된 사례에서 `mcp` 카테고리는 값이 1,039였고, 그 대화가 17~206개 스냅샷에
걸쳐 진행되는 동안 **한 번도 바뀌지 않았다** — 도구를 몇 번 호출했든 이
값은 그대로였다. 대화 도중에 새 MCP 서버를 연결하거나 끊는 경우는 이번
표본(31개 대화)에서 만나지 못했다 — 그런 경우까지 값이 고정인지는 확인하지
못했다.

## 토큰 상한에 가까워지면 무슨 일이 일어나는가 — 압축(compaction)

컨텍스트 창에는 상한이 있다(위에서 본 200,000~300,000 토큰). 대화 하나가
이 상한 가까이까지 찬 뒤 오래된 내용이 요약으로 눌러 담기는 지점을 실측으로
확인했다. 그 사례를 그대로 옮긴다(카테고리별 토큰 수일 뿐, 실제 요약 문장이나
대화 내용은 아니다 — 프롬프트·응답 본문은 이 조사에서 한 번도 읽지 않았다).

**압축 직전** (컨텍스트 총합 186,654 / 창 200,000 — 93.3% 사용)

| 카테고리 | 토큰 |
|---|---:|
| system_prompt | 517 |
| tools | 8,079 |
| rules | 3,026 |
| skills | 2,255 |
| mcp | 1,039 |
| subagents | 503 |
| summarized_conversation | 0 |
| conversation | 171,235 |

**압축 직후** (컨텍스트 총합 68,810 / 창 200,000 — 34.4% 사용)

| 카테고리 | 토큰 |
|---|---:|
| system_prompt | 517 |
| tools | 8,079 |
| rules | 3,026 |
| skills | 2,255 |
| mcp | 1,039 |
| subagents | 503 |
| summarized_conversation | 4,986 |
| conversation | 48,405 |

고정값인 여섯 카테고리는 전혀 안 바뀌었다. 바뀐 건 딱 둘이다 — `conversation`이
171,235에서 48,405로 줄고, `summarized_conversation`이 0에서 4,986으로
채워졌다. 정리하면:

- 이전 대화 내용 중 **122,830 토큰어치**가 요약 **4,986 토큰**으로
  바뀌었다(약 34:1 비율).
- 가장 최근 **48,405 토큰**은 압축 없이 원문 그대로 남았다 — 압축이 대화
  전체가 아니라 오래된 부분만 건드렸다.
- 이 사례에서 압축은 창의 93.3%가 찬 시점에 관측됐다.

## 더 많은 압축 사례 — 요약 크기의 분포

위 사례 하나는 압축 직전 스냅샷과 압축 직후 스냅샷이 같은 대화 안에서
순서대로 이어져 있어 전후 비교가 가능했다. IDE 쪽 저장소는 조각이 대화별로
순서 있게 묶여 있지 않아 같은 방식의 전후 비교는 어렵지만, `summarized_
conversation`이 0보다 큰 스냅샷만 따로 모으면 **압축이 이미 일어난 상태**의
사례를 더 모을 수 있다. CLI·IDE를 합쳐 이렇게 모은 서로 다른 스냅샷은
230개였다.

요약 칸(`summarized_conversation`) 값 자체의 범위는 **461 ~ 17,803 토큰**으로
넓게 퍼져 있었다. 몇 가지를 그대로 옮긴다(창 크기별로 하나씩, 카테고리별
토큰 수만):

| 창 크기 | summarized_conversation | conversation | system_prompt | tools | rules | skills | mcp | subagents |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 200,000 | 461 | 13,755 | 673 | 8,329 | 1,897 | 2,610 | 1,010 | 441 |
| 200,000 | 5,487 | 34,500 | 672 | 8,309 | 1,885 | 2,579 | 860 | 440 |
| 256,000 | 1,888 | 89,599 | 1,518 | 13,853 | 5,957 | 4,437 | 1,483 | 1,246 |
| 272,000 | 8,150 | 82,205 | 5,064 | 14,669 | 2,993 | 4,204 | 3,681 | 758 |
| 272,000 | 17,803 | 205,584 | 4,171 | 13,826 | 251 | 3,492 | 908 | 643 |

이 값들은 각 스냅샷의 "그 순간 상태"일 뿐, 압축 직전 값과 순서대로 짝지은
것은 아니다 — 위 CLI 사례처럼 전후 비교가 가능한 건 순서를 알 수 있는
경우로 한정된다.

## 얼마나 자주 일어나고, 얼마나 영향을 주는가 — 감도 실측

31개 대화·554개 관측 구간을 대상으로 두 가지를 측정했다.

**카테고리를 어떻게 고르든 결과는 같았다.** "전체 컨텍스트 증가량"과
"`conversation` 카테고리만의 증가량"을 각각 더해봤는데, 554개 구간 전부에서
완전히 같은 값이 나왔다(비율 1.00배). 고정값인 여섯 카테고리가 애초에 안
바뀌었으니 당연한 결과이지만, 실측으로 확인해두면 이후 계산에서 어느 쪽을
써도 상관없다는 뜻이 된다.

**압축은 드물지만, 한 번의 영향이 크다.** 554개 구간 중 컨텍스트가 오히려
줄어든(=압축이 일어난) 구간은 1개(0.18%)뿐이었다. 31개 대화 중에서도 압축이
관측된 건 1개 대화뿐이다. 그런데 그 압축 1건의 크기(117,844 토큰)가 전체
누적 증가량(1,009,463 토큰)의 **11.67%**에 해당했다. 즉 발생 빈도는 낮지만,
누적 통계를 계산할 때 이 한 번을 놓치면 전체 숫자가 두 자릿수 퍼센트로
어긋난다.

## 이 조사로 알 수 없었던 것

- **요청 하나, 턴 하나가 정확히 몇 토큰을 썼는지.** 이 breakdown은 스냅샷이지
  사용 로그가 아니다. 스냅샷 간 증가량을 구간 추정치로 쓸 수는 있어도, 그
  구간 안에 사용자 메시지와 모델 응답이 각각 몇 토큰인지는 가를 수 없다.
- **입력·출력·캐시 토큰의 구분.** 다른 AI 코딩 도구들은 API 응답에 이 구분이
  직접 찍혀 나오지만, Cursor의 로컬 저장소에는 이 구분이 없다.
- **압축 트리거의 정확한 임계값.** 93.3%에서 한 번 관측했을 뿐, 정확한
  기준선은 확인하지 못했다.
- **MCP 도구를 실제로 몇 번 호출했는지.** `mcp` 카테고리 값은 도구 호출
  횟수와 무관하게 고정이었다 — 무엇을 세고 있는 값인지는 확인하지 못했다.
- **대화 도중 새 MCP 서버를 연결했을 때의 변화.** 이번 표본에는 그런 사례가
  없었다.
- **IDE(Composer) 쪽 압축의 빈도·전후 비교.** 압축이 이미 일어난 상태의
  스냅샷 자체는 IDE 쪽에서도 다수(230개) 모을 수 있었지만, 조각들이 대화별로
  순서 있게 묶여 있지 않아 "몇 번에 한 번 압축이 일어나는지", "직전 값이
  얼마였는지"는 CLI만큼 확인하지 못했다.
- **압축이 실제 서버 요청량에 미치는 영향.** 이 조사는 로컬에 저장된
  컨텍스트 구성 스냅샷만 봤다 — 네트워크 트래픽은 확인하지 않았다.

## 요약

Cursor는 로컬에 완전한 토큰 사용 로그를 남기지 않는다. 대신 대화가 진행되는
동안 "지금 컨텍스트 창에 무엇이 얼마나 들어있는지"를 여러 시점에 걸쳐
스냅샷으로 남긴다. 이 스냅샷은 여섯 개의 고정 카테고리(시스템 프롬프트, 도구,
룰, 스킬, MCP, 서브에이전트)와 두 개의 변동 카테고리(실제 대화, 압축 요약)로
나뉘고, 고정 카테고리는 대화가 끝날 때까지 값이 바뀌지 않는다. 컨텍스트가
상한 가까이 찬 시점에 오래된 대화 내용이 큰 비율(실측 사례 기준 약 34:1)로
요약되는 것을 확인했다. 스냅샷 간 증가량을 이어붙이면 대화별 누적치를 계산할
수 있지만, 압축으로 값이 줄어드는 구간을 그대로 더하면(음수 증가량을 걸러내지
않으면) 표본 기준 11.67%까지 오차가 생길 수 있다.
