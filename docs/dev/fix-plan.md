# 수정 플랜 (실측 기반)

문서 감사에서 나온 결함 다섯 개의 수정 순서입니다. 이 문서의 모든 숫자는 **개발
머신의 실제 원장과 실제 로그 파일을 재서** 나온 값이고, 재는 과정에서 감사 당시의
서술 몇 개가 틀렸음이 드러났습니다. 그 정정도 함께 적습니다 — 틀린 근거로 세운
플랜은 틀린 곳을 고칩니다.

측정 시점 2026-08-22. 원장: claude 17,482건 / codex 18,853건 / gemini 12,319건.

## 재고 나서 바뀐 것

| 감사·검토 때의 서술 | 실측 결과 |
|---|---|
| Codex 를 `upsertUsageEvent` 로 옮기는 것이 방향 | **성립하지 않습니다.** upsert 는 `(provider, event_key)` 로 기존 행을 찾는데, codex 행 18,853개 중 **18,734개가 `event_key = NULL`** 입니다(claude·gemini 는 0개). 키로는 어느 행도 못 찾습니다 |
| `event_key` 는 로그의 누적 스냅샷으로 만들어져 재읽기에서 재현되므로 안전하다 | 파서에 대해서는 맞습니다(`codex/parser.mjs` 의 `usageEventKey`). 그러나 **저장된 행에 키가 없어서** 수리에는 쓸 수 없습니다. 맞는 사실이 무관한 사실이었습니다 |
| 차단하는 것은 `event_key` 일치 조기 return | **아닙니다.** 실측 18,853건 중 `event_key` 일치로 막히는 것은 **119건(0.63%)** 이고 **18,726건(99.33%)** 은 그 다음의 `shapeMatch` 가 막습니다. 결론("`ON CONFLICT` 만으로는 부족")은 맞고 지목한 기구가 틀렸습니다 |
| 커서를 0 으로 되감으면 `initial_cumulative` 로 합계가 부풀 위험 | **일어나지 않습니다.** 678개 파일 전량 재파싱에서 `(source_path, source_offset)` 으로 원장 행을 **18,853/18,853 = 100%** 찾았고 토큰이 **99.96%** 동일했습니다. 재해석은 결정론적입니다 |
| 기동마다 785.2 MB 재파싱이 무거운 비용 | 용량은 맞지만 **시간을 재지 않고 말했습니다.** 단일 스레드 전량 재파싱이 **4.86초** 입니다. 실비용은 "기동이 느려짐"이 아니라 "CPU·I/O 를 매번 헛씀 + 원장이 영구히 안 고쳐짐" 입니다 |
| 기간 합계·차트 결함은 provider 회계가 섞여서 생긴다 | 절반만 맞습니다. **최악 버킷은 혼합이 아니라 codex 단독**(1.95배)이고, provider 로 쪼갠 뒤에도 235개 중 **5개가 여전히 fallback** 입니다. 원인은 회계 혼합이 아니라 아래 6행입니다 |
| 총합만 있고 분해가 0 인 6행은 원장 결함이라 재파싱하면 고쳐진다 | **고쳐지지 않습니다.** 재파싱해도 `i=0 o=0 total=N` 그대로입니다 — **로그 자체가 그렇게 적혀 있습니다.** 그러므로 이 5개 버킷은 영구히 분해 불가이고, 화면은 숫자를 맞추는 대신 **분해 불가를 말해야** 합니다 |
| `usage-client.js` 가 401 을 삼킨다 | **삼키지 않습니다.** `error.status === 401` 로 정상적으로 던집니다(실측 확인). 버리는 곳은 `src/App.jsx` 이고, **빈 catch 세 곳이 아니라 다섯 지점**입니다 — 아래 1단계 표 |
| 빈 `catch` 세 곳 | **다섯 지점이고 두 개는 빈 catch 보다 나쁩니다.** `App.jsx:115` 는 `catch` 가 **아예 없어** 수동 재스캔이 조용히 죽고 unhandled rejection 이 됩니다. `App.jsx:83` 은 `subscribe(callback, onError)` 의 **`onError` 를 넘기지 않아** SSE 401 이 통째로 버려지고 EventSource 가 `retry: 3000` 으로 무한 재연결합니다 |

새로 발견한 것 하나: **원장에 536,028 토큰의 실제 중복 계상이 있습니다.** 8개 행이
재파싱 값의 약 2배로 저장돼 있고(예: 저장 252,678 / 재파싱 126,457), 양쪽 모두
항등식은 성립하며 `increment_source` 는 전부 `last_token_usage` 입니다. codex 총합의
0.028% 입니다.

## 1단계 — 재시작 후 조용히 멈추는 탭 (결함 D)

**먼저 하는 이유**: 원장을 건드리지 않고, diff 가 작고, 재시작마다 재현되며,
필요한 정보가 이미 클라이언트까지 도달해 있습니다. 되돌리기가 자유롭습니다.

실측한 현재 동작: 토큰은 프로세스마다 새로 생성되고, 옛 토큰의 REST 는
`401 {"error":"unauthorized"}`, SSE 도 401 입니다. `createUsageClient` 는
`error.status = 401` 을 붙여 던집니다 — **정보는 이미 클라이언트 경계까지 와 있습니다.**
버리는 곳은 `src/App.jsx` 다섯 지점입니다.

| 지점 | 지금 | 결과 |
|---|---|---|
| `App.jsx:77` `getSnapshot()` | `.catch(() => {})` | 첫 로드 실패가 무음 |
| `App.jsx:81` hook 상태 | `.catch(() => {})` | 칩이 `미확인` 으로 남고 이유 없음 |
| `App.jsx:83` `subscribe(...)` | **`onError` 를 넘기지 않음** | SSE 401 이 통째로 버려지고 `retry: 3000` 으로 무한 재연결 |
| `App.jsx:100` focus reconcile | `.catch(() => {})` | 탭 복귀 갱신 실패가 무음 |
| `App.jsx:115` 수동 재스캔 | **`catch` 가 없음** | 버튼이 조용히 죽고 unhandled rejection |

뒤의 둘이 빈 catch 보다 나쁩니다 — 하나는 오류 채널이 존재하는데 연결하지 않았고,
하나는 처리 자체가 없습니다.

**할 일**

- 다섯 지점이 모두 오류를 상태로 올립니다. `subscribe` 에는 `onError` 를 넘기고,
  115행에는 `catch` 를 만듭니다.
- 판단은 JSX 가 아니라 `src/shared.js` 의 헬퍼로 뺍니다 — 렌더 테스트 인프라가
  없으므로 이 저장소는 그렇게 단정합니다.
  `connectionState({ status, lastSnapshotAt })` 가 세 갈래를 냅니다:
  `stale-auth`(401 → "서비스가 다시 시작됐어요. 새로고침하면 이어집니다") /
  `unreachable`(그 외 실패) / `live`.
- 401 은 **자동 재발급하지 않습니다.** 토큰은 프로세스 능력이고 페이지에 주입되는
  값이라, 클라이언트가 스스로 새로 얻는 경로를 만들면 보안 경계가 무너집니다.
  새로고침 안내가 맞는 답입니다.
- 숫자를 지우지 않습니다. 낡은 값을 지우면 "0 토큰"으로 읽힙니다(R7). 값은 두고
  띠로 낡았다고 말합니다.

**완료 기준** — `test/shared-helpers.test.mjs`

- `connectionState({ status: 401 })` 가 `stale-auth` 를 내고 문구에 새로고침이 들어간다
- `connectionState({ status: 503 })` 는 `unreachable` 이고 `stale-auth` 와 다른 문구다
- 오류 없이 스냅샷이 있으면 `live` 이며 어떤 경고 문구도 만들지 않는다
- SSE 오류(`status` 가 없는 `Event`)도 `unreachable` 로 떨어지고 던지지 않는다 — EventSource 의 오류는 `Error` 가 아니라 `Event` 입니다

**규모** small · **되돌리기** 자유

## 2단계 — Codex 원장 (결함 A + B) — **초기화로 대체됨**

> **2026-08-22 갱신.** 사용자가 "프로젝트가 관리하는 DB는 초기화해도 된다"고 결정하고
> 설정 화면에 백업·초기화 기능이 들어갔습니다([menus/settings.md](./menus/settings.md#데이터-관리)).
> 그래서 아래의 **제자리 수리는 필요하지 않습니다.** 남는 것은 한 줄짜리 선행 조건
> 하나이고, 그것을 먼저 넣은 뒤 초기화하면 원장이 처음부터 완전해집니다.
>
> **선행 조건 (필수, 이미 반영됨)**: `insertUsageEvent` 의 INSERT 컬럼 목록에
> `tool_tokens` · `field_quality` · `parser_version` · `request_id` 가 없어서, 이 경로를
> 쓰는 provider(codex)의 행은 파서가 값을 실어 보내도 넷이 전부 NULL 이었습니다.
> **초기화만으로는 이 구멍이 그대로 재생산됩니다** — 그래서 순서가 "고치고 나서
> 초기화"입니다. `test/data-admin.test.mjs` 가 넷을 함께 못박습니다.
>
> **초기화가 무엇을 해결하는가**
>
> | 항목 | 제자리 수리 | 초기화 + 재측정 |
> |---|---|---|
> | `turn_index` 18,847행 | UPDATE 로 채움 | 처음부터 채워짐 |
> | `tool_counts` 16,415행 | UPDATE 로 채움 | 처음부터 채워짐 |
> | `parser_version` · `field_quality` · `request_id` | UPDATE 로 채움 | 처음부터 채워짐 |
> | 재해석 루프 | 수리 후 멈춤 | **아예 시작하지 않음** — `turn_index` 가 NULL 이 아니므로 `missingTurns` 가 false |
> | 536,028 토큰 중복 계상 8행 | 남음(토큰 불변이 안전성 근거) | **사라짐** — 재파싱이 올바른 작은 값을 냅니다 |
> | 되돌리기 | 함수 롤백 | 초기화 전 자동 백업 |
>
> 초기화가 더 많이 고치고 더 단순합니다. 아래 제자리 수리 기술은 **로그가 이미 지워진
> 구간이 있어 재측정이 손실을 뜻하는 경우**를 위한 대안으로 남겨 둡니다.

### (대안) 제자리 수리 — 초기화를 쓸 수 없을 때

**방향**: 충돌 시 **메타 컬럼만 UPDATE, 토큰 컬럼은 절대 건드리지 않음.**
`upsertUsageEvent` 로 전환하지 않습니다 — 저장된 키가 없어서 동작하지 않고,
그 함수의 stale 가드는 메타 갱신까지 건너뛰어 루프를 일부 파일에 남깁니다.

**조인 키는 `(provider, source_path, source_offset)`** 입니다. 실측 100% 적중,
세 provider 모두 완전 고유(codex 18,853 행 = 18,853 고유).

**할 일 — `service/store.mjs` 의 `insertUsageEvent` 한 곳, 변경 하나**

조기 return 들 **앞에**, 이 위치의 행을 메타만 갱신하는 UPDATE 를 둡니다.

1. `turnMeta` 를 계산한 직후, `(provider, source_path, source_offset)` 로 UPDATE 를
   시도합니다. `changes > 0` 이면 그 위치에 이미 행이 있다는 뜻이므로 **새로 적을
   것이 없어 `return false`** 합니다 — 다만 메타는 채워졌습니다.
2. `changes === 0` 이면 기존 로직을 그대로 지나갑니다. 두 조기 return
   (`event_key` 일치 · `shapeMatch`)과 `INSERT OR IGNORE` 는 **손대지 않습니다.**
   그 둘은 *다른 `source_path`* 에 같은 내용이 나타나는 경우(활성 세션이 아카이브로
   복사됨)를 막는 장치라 목적이 다르고, 이 UPDATE 는 그 경우 0건을 갱신하므로
   서로 간섭하지 않습니다.
3. `SET` 목록: `turn_index` · `tool_counts` · `touched_paths` · `parser_version` ·
   `field_quality` · `request_id`, 그리고 `event_key = COALESCE(event_key, ?)`.
   마지막 것이 NULL 이던 18,734행에 키를 채워, 이후 수리가 키 기반으로 싸집니다.
4. 토큰 여섯 컬럼과 `total_tokens` 는 `SET` 목록에 **넣지 않습니다.** 이것이 이 안의
   안전성 전체입니다 — 합계가 변할 경로가 코드에 존재하지 않습니다.

이 한 변경으로 충분합니다. 시연에서 18,853건 **전부**가 이 UPDATE 로 대상 행을
찾았고 빈 타격이 0건이었습니다 — 조기 return 을 고치거나 `ON CONFLICT` 를 쓰는
추가 변경이 필요하지 않았습니다.

> 처음 세운 안은 조기 return 두 개를 `SELECT id → UPDATE` 로 바꾸고 `INSERT OR
> IGNORE` 를 `ON CONFLICT DO UPDATE` 로 바꾸는 것이었습니다. 시연해 보니 선행
> UPDATE 하나로 세 경로가 모두 덮여, 더 작은 diff 로 같은 결과가 납니다. 위
> 기술이 **실제로 재 본 쪽**입니다.

**수렴 확인**: `hasUnattributedTurns` 는 `turn_index IS NULL` 을 봅니다. 수리 후
17,394행이 실제 턴 번호를, 1,453행이 0(경계 미확인 — 서브에이전트·경계 앞 사용량)을
받습니다. **0 은 NULL 이 아니므로** 판정이 false 가 되고 루프가 멈춥니다.

**하지 않는 것**

- `turn_index` 를 sentinel 0 으로 일괄 채워 판정만 끄기. `getSessionFlow` 가 이미
  `COALESCE(turn_index, 0)` 이라 화면은 안 바뀌지만, 원래 턴 1·2·3 이었어야 할
  17,394행을 영구히 0 으로 굳혀 `turns` 2,718 경계와 끊고 self-heal 을 영구히
  끕니다. 표시가 아니라 **복구 불능**이 문제입니다.
- 판정 결과를 `provider_scan_state` 에 기억해 파일당 한 번만 시도하기. 원장은
  그대로 둔 채 재시도만 포기하는 것이라, Gemini 가 `#resetLegacyIdentity` 로
  원장을 비우고 다시 읽는 것과 정반대 방향입니다.

**완료 기준** — `test/codex-store.test.mjs`

- 옛 스타일 행(`event_key` NULL · `turn_index` NULL)을 심고 같은 이벤트를 다시
  넣으면 **행 수가 안 늘고**, `turn_index`·`parser_version`·`event_key` 가 채워지고,
  토큰 여섯 컬럼이 **바이트 단위로 그대로**다
- 재파싱 값이 저장값과 **다른** 이벤트가 와도 토큰 컬럼은 안 바뀐다(536,028 토큰 8행 케이스)
- 같은 내용이 **다른 `source_path`** 로 오면 여전히 새 행이 되지 않는다 — 아카이브
  사본 회귀 방지. 선행 UPDATE 가 그 경우 0건을 갱신하고 조기 return 이 그대로
  동작함을 확인하는 단정입니다
- 그 위치에 행이 **없으면** 선행 UPDATE 가 0건이고 정상적으로 INSERT 된다 — 새
  이벤트 경로가 죽지 않았음을 확인
- 같은 파일을 세 번 스캔해도 합계·행 수·턴 수가 늘지 않는다

**규모** medium · **되돌리기** 쉬움 — 함수 하나 롤백. 토큰을 안 건드리므로
데이터가 남기는 흔적은 "메타가 채워진 것"뿐이고, 그것이 잘못돼도 다시 재해석하면

## 3단계 — 기간 합계와 차트의 겹친 분해 (결함 C)

두 부분이고 **둘 다 해야** 합니다. 하나만 하면 화면 안에서 서로 어긋납니다.

### 3-1. provider 를 키에 넣어 쪼갠다

`src/views/UsageView.jsx` 의 `buckets` 는 `merged.get(point.bucketStart)` 로
**provider 를 키에서 빼고** 합칩니다. 그 합산 버킷이 `periodTotals` 와
`<StackedBars>` 양쪽에 들어갑니다. 그래서 패널만 고치면 차트가 틀린 채 남습니다.

실측 (일 버킷 210개): 29개가 fallback, 조각 합이 총합보다 **10.0% 과다**.
월 버킷은 **20.6% 과다**. 개별 막대는 최대 **1.98배**, y축 max 는 1.00~1.06배.

헬퍼는 `src/shared.js` 로 빼서 대시보드와 공유합니다 — 대시보드의 `tokenSplits` 가
이미 같은 일을 하고 있어 로직이 두 곳에 있습니다.

- `buildProviderTokenSplits(providers, tokensByProvider)` — provider 마다 자기
  회계로 `decomposeTokens` 하고 회계 이름을 붙임
- `resolvePeriodBreakdown({ providerFilter, splits, mergedDecomposed })` →
  `{ layout: 'providers' | 'categories', categories, notice }`.
  **핵심 단정: `layout === 'providers'` 일 때 `categories` 는 `null`** — 합산
  fallback 다섯 칸을 화면에 넘길 경로가 아예 없어야 합니다

### 3-2. 분해 불가를 말한다

이것이 없으면 3-1 로도 부족합니다. 실측: provider 로 쪼갠 (버킷 × provider) 235개
중 **5개가 여전히 fallback** 이고, 전부 codex 이며 원인은 총합만 있고 분해가 0 인
6행입니다. **재파싱해도 안 고쳐집니다 — 로그가 그렇게 적혀 있습니다.** 그러므로
숫자를 맞추는 것은 답이 아니고, 모른다고 말하는 것이 답입니다(R4·R7).

`decomposeTokens` 는 이미 `nested: false` 로 그 사실을 내고 있는데 `UsageView` 의
JSX 가 읽지 않습니다. 대시보드는 `겹침 미확인` 을 붙입니다.

문구:

- 전체 필터 · 합산 fallback → *"입력 범주 정의가 provider마다 달라, 전체를 다섯
  칸으로 합치면 조각 합이 맞지 않습니다. 아래는 provider별로 나눈 값입니다."*
- 단일 provider 인데 `nested:false` → *"이 기간에는 토큰 범주가 겹치는지 판단할 수
  없어 원래 범주를 그대로 표시합니다 — 조각 합이 합계와 다를 수 있습니다."*

### 3-3. 거짓 부제

`src/views/UsageView.jsx:177` 의 *"캐시 읽기는 입력에 합산하지 않습니다"* 는 Claude
회계 기준입니다. codex·gemini 는 `input ⊃ cached` 이고, 합산 fallback 은 raw
`input` 과 `cached` 를 따로 쌓으므로 **부제가 거짓이 되는 경우가 정확히 결함이
발동하는 경우**입니다. 3-1 로 조각이 provider별로 갈리면 참이 되지만, 부제가
회계를 단정하지 않도록 고치는 편이 안전합니다.

**완료 기준** — `test/shared-helpers.test.mjs`

- 회계가 다른 두 provider 의 totals 를 더해 `decomposeTokens` 하면 `nested === false`
  이고 조각 합이 총합과 다르다 (이 결함의 존재 자체를 못박음)
- 그 입력으로 `resolvePeriodBreakdown` 을 부르면 `layout === 'providers'` 이고
  `categories === null` 이다 — **합산 다섯 칸이 화면에 갈 경로가 없다**
- provider별 split 은 각자 `nested === true` 이고 조각 합이 그 provider 총합과 정확히 같다
- 단일 provider 인데 `nested === false` 면 `notice` 가 나오고, 그 문구가 "조각 합"
  또는 "겹침"을 포함한다
- 총합만 있고 분해가 0 인 실제 모양(`i=0, o=0, total=N`)을 넣으면 `nested === false`
  다 — 6행이 만드는 상황을 픽스처로 고정

**규모** medium · **되돌리기** 자유 (화면·헬퍼만)

## 사용자 판단이 필요한 지점 — 여기서 멈춥니다

**536,028 토큰(codex 총합의 0.028%) 중복 계상 8행을 정정할지.**

2단계는 토큰을 건드리지 않으므로 이 8행은 부풀린 값으로 **남습니다.** 재파싱 값이
올바른 값으로 보입니다 — 저장값이 재파싱값의 약 2배이고 양쪽 다 항등식이 성립하며,
`last_token_usage` 증분이 두 번 계상된 모양입니다.

- **남긴다**: 합계가 절대 변하지 않습니다. 되돌릴 것이 없습니다. 대신 원장에 알려진
  0.028% 부풀림이 남습니다.
- **정정한다**: codex 총합이 1,891,859,672 → 1,891,323,644 로 **줄어듭니다.**
  "정직한 불완전 측정" 원칙은 이쪽을 지지하지만, **과거 숫자를 바꾸는 되돌릴 수 없는
  변경**이고 사용자가 전에 본 수와 달라집니다.

정정하기로 한다면 2단계와 **분리된 별도 단계**로, 대상 8행을 먼저 파일에 적어 두고
DB 를 복사한 뒤에 합니다. 2단계에 섞으면 "메타만 건드린다"는 안전성 근거가 사라집니다.

지금은 **남기는 쪽으로 두고** 별도 결정을 기다립니다.

## 초기화와 무관하게 남는 결함 둘

병렬로 돌린 검토가 짚었고 코드로 확인했습니다. 원장을 비워도 그대로 남습니다 —
적재된 데이터가 아니라 **수집 루프**의 문제입니다.

### R1. `reconcile()` 에 패스 단위 재진입 가드가 없습니다

`setInterval(() => this.reconcile('interval'), 5000)` 이 이전 패스가 끝났는지 보지
않고 5초마다 새로 시작합니다(`codex/collector.mjs`). 파일 단위 `scanInFlight` 맵이
같은 파일의 동시 스캔은 합쳐 주지만, `discoverFiles()` 와 트리 전체를 걷는
`refreshWatchers()` 는 패스마다 새로 돕니다.

지금 이것이 특히 나쁜 이유는 되감기와 겹치기 때문입니다 — 되감기 패스 하나가 단일
스레드로 약 5초인데 타이머가 5초라, 끝나기 전에 다음 패스가 시작됩니다.
**초기화하면 되감기가 사라져 피해가 크게 줄지만**, 가드가 없다는 사실 자체는 남습니다.

### R2. 턴 이벤트가 `counters.changed` 를 무조건 세웁니다

`codex/collector.mjs` 의 배치 루프에서 `event.type === 'turn'` 이면 조건 없이
`counters.changed = true` 입니다. `upsertTurn` 은 `ON CONFLICT DO UPDATE` 라 같은
경계를 다시 써도 "변경"으로 보고하므로, **아무것도 실제로 바뀌지 않은 재읽기도
스냅샷 브로드캐스트를 유발합니다.**

`#emitUpdate` 는 `warmup.phase === 'scanning'` 구간만 스로틀하고(`engine.mjs`),
`ready` 이후에는 스로틀이 없습니다. 둘이 겹치면 재읽기가 도는 동안 SSE 가 계속
울립니다.

고치는 방향: `changed` 판정을 실제 삽입/갱신 건수로 바꾸고, `#emitUpdate` 에
`ready` 구간 스로틀(trailing emit 포함)을 넣습니다. 둘 다 원장을 건드리지 않습니다.

## 새로 열린 항목

- **`turns` 고아 경계 182개** (2단계 시연에서 발견). 경계는 있는데 그 턴에 사용량

- **별칭 PUT 의 `provider` 기본값** — 판정 보류. 병렬 검토 결과가 오면 채웁니다.
